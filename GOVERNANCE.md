# Governance

This project is currently maintained by a single maintainer, [Joseph Searle](https://github.com/JosephSearle). This document explains how that works in practice, and what happens as that changes.

## Roles

There is one role today: **maintainer**. The maintainer has final say on what gets merged, how the catalog and site evolve, and how this document itself changes.

**Becoming a maintainer.** There are no other maintainers yet. A contributor could become a co-maintainer after a sustained track record of accepted, well-scoped contributions (skills or site changes) and active participation in reviewing others' PRs — added at the current maintainer's discretion. This isn't a formal nomination/vote process, because there's no group to run one; it's a statement of intent, not a rule that's been exercised yet.

**Losing the role.** If a maintainer stops participating (no activity — merges, reviews, or responses to issues — for an extended period, informally: several months), they're considered inactive and any co-maintainers at the time may take over decisions without waiting on them.

**Continuity / bus factor.** If the sole maintainer becomes permanently unavailable and hasn't designated a successor, anyone who has been an active, trusted contributor may request maintainer access via a GitHub issue, and the community can use that issue thread to reach consensus on next steps. This is a real gap today — there is no co-maintainer as of this writing — so if you're contributing to this project, know that continuity would need to be handled ad hoc if it came to that.

## Decisions

Day-to-day decisions (accepting a PR, tweaking a skill, adjusting site behavior) are made by the maintainer directly, informed by discussion in the relevant issue or PR — see [CONTRIBUTING.md](CONTRIBUTING.md) for the routine review/merge mechanics. There's no separate decision log beyond the issue/PR history itself, since there's no group whose decisions need to be reconciled.

Larger changes — new skill categories, a change to how the catalog or site is structured, or a change to this governance model — should still start as a GitHub issue per [CONTRIBUTING.md](CONTRIBUTING.md#minor-vs-major-changes), so there's a public record of the reasoning even though one person is deciding.

## Conflicts

Because there's a single maintainer, there's no peer body to escalate a disagreement to today. If a contributor disagrees with a decision, the path is to raise it in the relevant issue or PR and make the case; the maintainer has final say. If and when this project gains additional maintainers, this section should be updated to describe how they resolve disagreements among themselves (e.g., consensus-seeking with a documented fallback) rather than leaving that undefined.

## Changing this document

Changes to GOVERNANCE.md follow the same process as any other change: open a PR, and if it's a structural change (e.g., moving from a single maintainer to a maintainer council), open an issue first per the [CONTRIBUTING.md](CONTRIBUTING.md#minor-vs-major-changes) guidance on major changes.
